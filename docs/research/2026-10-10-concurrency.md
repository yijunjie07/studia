# AI 答题与自动学习并发可行性研究

研究日期：2026-10-10。范围：当前工作区的一手源码与现有离线测试；没有调用真实平台或模型，没有读取用户密钥，没有修改生产代码。下文明确区分现状、工程建议和未验证的外部条件。

研究基线：Git `6568b2f`。用户确认关注 AI 答题和自动学习。

## 总体判断

| 方向 | 当前状态 | 可行性判断 |
| --- | --- | --- |
| AI 答题 | 试卷和题目均串行 | 同卷题目生成适合有界并发，跨卷、补答和提交继续顺序处理 |
| 自动学习 | 课程及资源均串行 | 可拆出资源级并发，但须先隔离状态、完善超时及响应校验，并验证平台允许的写入并发 |

建议先推进 AI 题目并发，再处理学习资源并发。没有实测依据承诺提速倍数；线程数也不等于平台或服务商允许的请求频率。

## AI 答题结论

**可以改造为有限并发，但当前没有 AI 任务并发调度能力。优先选择“同一份试卷的多个题目并发请求 AI，跨试卷继续串行”，不建议直接并发调用现有 `run_paper()`。** 依据是题目请求没有对话历史依赖，而报告、人工补答、时间检查和提交是一套有顺序的状态机；现有实现分别见 `ai/client.py:126`、`ai/runner.py:219`、`ai/runner.py:260`、`ai/runner.py:293`。建议的收益方向是缩短模型网络等待；实际加速比、可用并发数、服务商和平台限制尚未验证，不能从源码承诺具体倍数。

## 已确认的执行链

1. `Application.execute_ai()` 先验证模型连接，再创建一个 `AIClient`、一个 `ExamAPI` 和一个 `AnswerRunner`，随后逐份 `run_paper()`；错误、暂停或交卷状态未知会停止后续试卷。见 `app.py:258`、`app.py:268`、`app.py:281`。
2. 一份试卷先创建排他锁，读取历史与试卷，检查作答记录归属、是否仍为草稿、题数、剩余时间，再开始答题。取卷可能启动作答记录/计时，不能视为没有副作用的预读取。见 `ai/runner.py:131`、`ai/runner.py:183`、`ai/runner.py:205`；取卷副作用的现有协议说明见 `AIMoocMain/exam_api.py:89`。
3. 原题与材料子题按嵌套循环顺序解析、请求 AI、校验、记录答案、写报告。每题 AI 调用是阻塞式 `requests.Session.post()`，不串接此前答案或会话标识。见 `ai/runner.py:219`、`ai/runner.py:241`、`ai/runner.py:288`、`ai/client.py:126`、`ai/client.py:141`。
4. 全卷完成后停止心跳并检查时间，确保无失败题，再复查草稿状态，持久化 `submitting`，整卷提交一次，然后查询是否确认提交；未知结果不自动重发。见 `ai/runner.py:293`、`ai/runner.py:303`、`ai/runner.py:312`、`AIMoocMain/exam_api.py:118`。

## 并发边界与阻塞点

| 方面 | 当前源码事实 | 并发含义／建议 |
| --- | --- | --- |
| 题目独立性 | `prepare_question()` 构造新的题目字典；材料子题携带母题文本和原序号。AI 请求仅选择公开题目信息，不带会话历史（`ai/questions.py:27`、`:63`、`ai/client.py:127`）。 | 可以独立生成答案；不能假定所有输入是深复制，`raw_options` 仍引用解析数组，工作线程应只读。 |
| AI 客户端 | 一个客户端持有一个 `Session`；连接测试会修改 `config.api_format`（`ai/client.py:105`、`:119`）。 | 先串行完成探测并固定配置，再为工作线程提供独立客户端/会话。源码没有给出共享 Session 的线程安全承诺，不能仅凭能创建线程就认定安全。 |
| 服务商限制 | 408、429、5xx 和网络错误被标为可重试；每题最多 3 次尝试，间隔固定 1 秒、2 秒（`ai/client.py:146`、`:169`、`ai/runner.py:115`）。 | 当前没有统一并发闸门、每分钟限额、令牌预算、`Retry-After` 或退避抖动。并发后独立重试可能形成集中重试；需服务商级统一限流和冷却策略。 |
| 故障停止 | 不可恢复服务错误立即停止当前卷；可重试服务故障耗尽后，有人工回调时可补答，否则停止；上层再停止队列（`ai/runner.py:254`、`app.py:281`）。 | 并发版本必须停止派发尚未启动的题目，标记/处理已在途请求，并禁止后续结果把终态覆盖成成功；简单取消 Future 不等于中断阻塞 HTTP。 |
| 顺序和身份 | 原始题序 `number`、子题序 `child_number` 进入提交记录，普通题/子题身份还经过集合去重（`ai/questions.py:100`、`ai/runner.py:232`）。 | 先在协调者完成解析及去重，用稳定序号关联 Future；不能用完成顺序产生题号或报告顺序。平台是否接受乱序数组未验证，应保留当前顺序。 |
| 报告写入 | 每题都更新同一个列表和文件；JSON 用固定 `.json.tmp` 后替换，Markdown 直接写。报告按账号、课程、试卷确定路径；`run_paper()` 对该路径持有 `.lock`（`ai/runner.py:63`、`:69`、`:131`、`:288`）。 | 现有锁保护同一报告路径的整次运行，不保护同一运行内部多个写线程。必须让单一协调者写报告。锁依赖相同根目录和课程目录名，不能当成跨设备或平台级互斥；不同输出根目录或不同课程名可绕过同一身份的本地路径锁。 |
| 人工补答 | 失败后先保存 `paused` 报告，再同步等待 `manual_answer()`；退出返回时结束整卷。UI 会停止并恢复共享 Live 显示（`ai/runner.py:260`、`ui.py:288`）。 | 补答必须留在主协调流程，不能让多个工作线程同时读取终端。建议需要补答时暂停派发，保存已完成结果，顺序处理补答；等待期间已在途结果的收集规则需明确。 |
| 计时和心跳 | 已有后台线程每 10 秒发送真实经过时间，仅自动提交模式启用；该时钟共享传入的 `ExamAPI`，停止后等待线程结束，结束不了便阻止交卷（`ai/runner.py:17`、`:35`、`:55`、`:213`）。 | 此线程不是题目并发调度。保留每卷唯一时钟；超时/心跳失败时禁止新任务和交卷，协调者停止接收会改变终态的结果。跨卷并发会额外同时启动多个计时器与平台请求。 |
| 回调与共享 runner | runner 保存共享 `reused`、AI/API/进度回调；`Reporter.emit()` 在调用线程直接执行回调，没有事件队列或任务标识（`ai/runner.py:103`、`:132`、`reporting.py:7`、`:21`）。 | 不能直接将共用 runner 放进线程池。题目工作线程只返回结果，协调者更新进度、报告与人工交互。 |

## 建议的最小改造方向（尚未实施）

采用小型有界线程池即可利用现有同步 HTTP 接口，无需为此先整体改成 `asyncio`。只把单题模型生成与其可重试过程放进工作线程；主协调流程负责题目解析、身份去重、派发窗口、结果关联、答案校验、人工补答、报告写入和最终整卷提交。普通题、材料子题均保留原始序号；所有输入按只读使用。依据是网络等待点集中在 `ai/client.py:141`，而状态与平台写操作集中在 `ai/runner.py:219` 至 `:330`。

并发数保留 `1` 的兼容模式，可将 `2` 作为首次离线验证的候选值；这只是工程起点，不代表服务商配额允许 2 路。应有配置上限与统一限流，重试不能额外突破并发预算。连接探测在启动工作线程前完成。报告只由协调者写，不能让每个 Future 调用现有写报告和 UI 逻辑。

跨卷保持串行，避免扩大现有“停止队列”和单终端补答的语义变化，也避免提前打开多份可能开始计时的试卷。最终提交仍保持：全题有效 → 时钟停止且无误 → 草稿状态复查 → 持久化 `submitting` → 一次提交 → 确认结果。不能把交卷放进可重试任务池。当前源码只证明本地防重复措施；它没有证明服务器支持幂等键或跨客户端原子去重（`AIMoocMain/exam_api.py:113`）。

若进入实现，建议以可控事件/屏障和假 HTTP 传输验证以下行为，而不靠真实平台压测：

- 请求确实有重叠且在途数不超过上限；并发数为 1 与当前行为一致。
- 强制乱序返回、复合题、重复题 ID，仍正确关联报告顺序与 `questionNo`/`paperSubId`。
- 429/5xx、鉴权失败和时间到期时停止派发；全局冷却及单题重试预算生效；已完成题不重发。
- 人工补答同时只出现一个输入提示，取消后不再提交，晚到结果不覆写 `paused`/`error`。
- 报告 JSON/Markdown 和累计进度由单一写者更新，最终提交只发生一次且必须包含全卷有效答案。
- 真实线程竞争同一路径锁、心跳停止和 HTTP 挂起的有界退出；测试必须区分“停止派发”和“已在途请求停止”。

## 外部未知

本次没有核验所配置服务商的 RPM、TPM、最大并发、429 响应头规范、排队和计费行为，也没有测试平台是否允许同账号多卷同时计时或是否接受乱序答案。现有源码没有这些保证。因此能确认的是**软件结构允许把独立 AI 生成改为有界并发**，而不是“现有版本已支持并发”或“任意并发数均可安全运行”。

## 自动学习并发可行性

### 当前执行链与优先粒度

当前主入口为 `StartWork.main → Application.run → CourseWorkspace → Application.study`，按平台调用 `AIMoocHandler` 或 `ZYKMoocHandler`。两种 handler 都顺序遍历课程，再递归顺序处理资源。当前课程列表配置为单选，因此仅把课程循环改成并发，对正常的“进入一门课再自动学习”操作没有加速效果；更有价值的候选粒度是**当前课程内互相独立的资源**。来源：`StartWork.py:35–44`、`app.py:179–188,287–290`、`course_flow.py:69–81`、`ui.py:530–535`、`AIMoocMain/main.py:43–54,74–103`、`ZYKMoocMain/main.py:44–55,74–93`。

旧代码 `MoocMain/lookVideo.py:150` 已用 `asyncio.gather` 批量上报，但当前上述学习入口调用的是另两套 handler。这不能作为当前版本已经支持学习并发的证据，也不能证明当前平台接受相同行为。

### 源码中的障碍

| 位置 | 事实 | 对并发的影响 |
| --- | --- | --- |
| `AIMoocMain/main.py:49–53,76–78,143–146` | 完成记录 `study_record_list` 和课程成败标记保存在 handler 实例上 | 同一实例并行多课程会覆盖完成记录、混淆结果；同课程并行资源也应汇总独立结果，而不是依赖共享标记 |
| `ZYKMoocMain/main.py:50–55,153–156` | 同样用实例级成败标记统计课程 | 需要明确每个资源的结果及课程汇总规则 |
| `base/api_client.py:12–20,22–60` | 一个客户端持有一个可变 Session；GET/POST/PUT 都未设置 timeout，异常被转换为 None | 不能把共享 Session 当作已验证可安全并发；慢请求可能长期占住全部工作线程，且上层无法区分限流、鉴权失败和写入结果未知 |
| `base/util.py:72–84` | 获取 MP3 时长也有无超时的流式请求 | 只给 BaseAPIClient 增加超时仍不足以保证任务能停止 |
| `AIMoocMain/main.py:178–196`、`AIMoocMain/api.py:161–185` | 每个资源等待 0.5–1.5 秒再写学习记录；MOOC 返回原始 JSON，上层只访问 msg 后就标记处理成功 | 多个线程的随机等待不能代替账号级限流；业务失败若仍含 msg，当前逻辑不足以证明保存成功 |
| `ZYKMoocMain/main.py:146–156`、`base/util.py:22–54` | 资源库等待 1–3 秒，响应经 parse_response 解包 | 必须保留平台差异，明确成功响应形态，不能直接照搬 MOOC 原始响应判断 |

这里的“代码可改造”与“平台认可同时上报多个学习资源”是两个不同结论。源码展示了带 `courseInfoId/sourceId` 等标识的单资源写入，但未给出同账号并发限制、资源解锁顺序、写入幂等性或学习记录结算规则。来源：`AIMoocMain/api.py:161–185`、`ZYKMoocMain/api.py:109–127`。因此平台写入并发目前只能列为**有条件可行、待协议和实际行为验证**。

### 后续实现候选，尚未实施

1. 将目录发现、已完成判断和待处理资源收集分开；每项资源携带完整课程/父节点/资源标识，使用不可变的完成记录快照并去重。
2. 使用有上限的线程池处理独立的资源读取/准备工作，匹配现有同步 requests。协调者负责收集结果、课程状态与 UI；工作线程各自持有 Session，复用认证信息而不重复交互登录。
3. 先补齐读取/写入超时与错误分类，MOOC 学习记录保存须验证业务返回码。写入超时不能视为“肯定未成功”，应查询记录确认，避免盲目重发。
4. 账号级请求节流独立于线程数；第一阶段可并行只读准备、串行记录写入。只有确认平台允许独立资源并行记录后，才试验 2 个资源同时执行，再根据结果决定是否提升。2 是实验起点，不是已知的平台配额。
5. 去重键至少包括平台、账号、课程和资源。同一资源不得重复调度；存在前置解锁关系的资源按依赖顺序处理。
6. 停止时不再派发新任务，取消未启动任务，等待在途请求结束或超时并汇总真实结果。现有同步请求无法靠取消 Future 强制中断。

上述内容是可行性建议，不是已批准的产品设计或已实现功能。

## UI、范围和验证补充

`TerminalUI` 的日志、进度事件和渲染已使用 `RLock`（`ui.py:129,175–216`），这是可复用的基础；但界面只有一个主任务进度和一个“本卷题目”进度（`ui.py:139–140,185–208`），`ProgressEvent` 也没有独立任务 ID（`reporting.py:7–14`）。多个 worker 直接各发 begin 或已完成数量会相互覆盖。适合由协调者统一发送累计进度；若未来同时展示多份试卷/多个操作，则需要独立任务标识和状态模型。

本轮用户范围为 AI 答题和自动学习；不包含导出加速，也不默认把学习与答题两个菜单操作同时启动。后者还涉及共享账号的平台请求预算和多任务交互，当前工作区按一次一个操作执行（`course_flow.py:69–81`）。

其中 `tests/test_ui.py:173–211` 验证学习部分失败统计、回调异常隔离，以及 AI 交卷结果未知时不启动下一份试卷。它们是当前串行行为的基线，**并未验证新并发实现**。本轮未修改生产代码，未读取真实凭证、调用真实课程写入接口或消耗 AI 额度。

学习并发后续验收应覆盖：最大在途数量受控；不同课程完成记录互不污染；同资源只写一次；失败响应不计成功；部分失败可准确汇总；429/鉴权失败能停止或退避；写入超时保留未知状态；取消后不再派发；界面累计进度单调且最终准确。平台并发上限、真实吞吐提升及写入语义仍需单独验证。
